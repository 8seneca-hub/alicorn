What Alicorn ships

Everything below is grounded in the Orca source tree. Each row is tagged with how much work it actually is: inherited already works today, extends has a real foundation to build on, and net-new has to be built from scratch. The ratio is the point — most of this platform already exists.

inherited Already in Orca today

Agents & execution

  • Parallel git worktrees — one isolated checkout per task; fan one prompt across several agents and compare.
  • Folder workspaces — a workspace with no repo checkout. AgentSessionWorkspaceKind = 'git-worktree' | 'folder'. This is what lets non-engineers in.
  • Multiple agent backends — Claude Code, OpenClaude, Codex, Grok, OMP, plus other TUI agents. Each is a user-installed binary; Orca never redistributes them.
  • Orchestration layer — runs, task DAGs, dispatch, workers, blocking ask/reply, decision gates, escalation, federation, worker_done. Agent-agnostic and already the substrate for hand-offs.
  • Agent teams — Claude Code's native leader/teammate mode, hosted by faking a tmux server. Claude-Code-only.
  • SSH execution — the execution host owns execution; loss of contact is never death. Verdicts are live / unverifiable / exited.
  • WSL, and a real terminal — xterm with multiplexing, snapshots and orphan cleanup.
  • Computer use + embedded browser — drive a browser or the desktop when the CLI is not enough.

Work tracking

  • Four trackers — GitHub, GitLab, Linear, Jira, behind one TaskProvider registry.
  • Board that writes back — dragging a card between columns already calls the tracker's update mutation. Two-way sync is not new work.
  • Workspace kanban — worktrees themselves arranged in status lanes, with pointer drag.
  • Diff review + AI annotation — review a change and have the agent annotate it.
  • Editors and viewers — Monaco, file explorer, quick open.

Skills & extensibility

  • Skill system — discovery, install, bundling, sharing, and per-agent skill selection. Already most of what a "role" needs.
  • Skill transfer — over SSH and the relay, plus cloud upload and a bundle manifest.
  • Plugins — with a remote kill-list for revoking a bad one.
  • MCP config management — the route by which Drive and SharePoint will connect.
  • CLI (orca) — worktrees, terminals, orchestration, skills, browser, computer use, automations.

Voice & automation

  • Speech-to-text, offline — sherpa-onnx running whisper, paraformer, senseVoice, nemo-ctc and transducer models locally. Audio need never leave the machine.
  • Cloud STT — OpenAI transcription as an alternative, with its own key store.
  • Dictation UI — already wired into the renderer.
  • Automations on a schedule — cron, interval and one-shot, scoped to a project or a folder workspace.

Platform

  • Org membership — members, invites and role changes, against the Orca Account service.
  • Mobile companion — iOS and Android apps that pair through the relay to monitor and steer agents.
  • Web runtime + relay — the existing path to a browser client, and the reason "desktop now, web later" is credible.
  • Eight languages — en, zh, ja, ko, es, fr, pt, uk, with parity enforced in CI.
  • macOS, Windows, Linux — with the platform hazards already documented and ratcheted in tests.
  • Auto-update, telemetry with opt-out, artifacts and share links.

net-newextends What Alicorn adds

Members net-new

Orca has agents and it has skills, but nothing that binds them into a named, reusable thing. This is the central new object.

  • The Member entity — name, role, agent backend, attached skills, permission mode, workspace kind and system rules, saved and reused.
  • A member library — define "Code Review" once, use it on every project.
  • Role identity — each role carries a hue mapped onto a token that already means that thing, so the agent map stays readable.

Cross-agent teaming net-new

Today's teams are Claude Code's own, emulated through tmux — so a Grok analyst cannot hand work to a Claude developer.

  • A mailbox Alicorn owns — leader and teammates across different backends, not one vendor's implementation.
  • Visible hand-offs — worker_done → handed to Code Review appears in the transcript, with provenance.
  • Return paths — findings go back to the member that produced the work, and the loop is legible.

Workflows extends

Orchestration builds DAGs at runtime, but nothing authors or shows them. This makes the graph a first-class, editable object.

  • Authored templates — stages, the member that owns each, and the trigger between them, saved per project.
  • The canvas — see the whole flow, including the return edge when review finds something.
  • Live overlay — which stages are running right now, on the same graph.

Board automation extends

The board and the orchestration layer both exist. Nothing connects a column change to a dispatch — that rule engine is the missing piece.

  • Custom columns mapped onto workflow stages.
  • Actions bound to a transition — "In Progress → In Review" dispatches Code Review; "→ Done" closes the ticket in the tracker.
  • The review loop — the reviewer reports back to the developer member to fix, without a human relaying it.

Integrations extends

  • Plane — a fifth provider in the existing TaskProvider registry, with the same two-way board sync the others get.
  • Drive and SharePoint — connected through the MCP layer that already exists, so a BA or PM can produce documents from a folder workspace.

Voice & org extends

  • Intent routing — transcription already works; turning "create a worktree for PAY-3021" into the operation is the new part.
  • Org skill catalog — curated, installable skills per role, governed centrally.
  • Shared org seats — members run on each employee's own machine today; a pooled org subscription that syncs is a later phase.

One caveat worth stating plainly: the Orca Account service that backs org membership is not in the open-source repo. Company-wide identity is the one dependency that has to be built or replaced before this is a platform rather than a single-user tool.
