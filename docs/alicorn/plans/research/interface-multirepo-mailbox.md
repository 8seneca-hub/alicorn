**Mailbox today**

- `src/main/runtime/orchestration/types.ts:229-246` — `MessageRow {id, run_id, delivery_contract?, from_handle, to_handle, subject, body, type, priority, thread_id, payload, read, sequence, created_at, delivered_at, sender_pane_key}`. `MessageDeliveryContract = 'legacy_direct'|'current_delivery'|'audit_only'`. `MessagePriority = 'normal'|'high'|'urgent'`.
- `src/main/runtime/orchestration/db/schema/create-core-tables-sql.ts` — `deliveries` table exists: `{id, run_id, consumer_generation, message_ids, status: 'outstanding'|'acknowledged'|'fenced', created_at, acknowledged_at}`. Ack is tracked per-delivery-batch, scoped to one `run_id`.
- `src/main/runtime/rpc/methods/orchestration-recipient-routing.ts:50-166` — `resolveBareOrchestrationRecipient`: resolves a bare terminal handle to a canonical address — `run:<id>` (pane bound to a live run), `dispatch:<id>` (active dispatch mailbox owner), or a historical `run:<id>` from `getRunMailboxOwnerIdsForHandle`; falls back to the raw handle with a `legacy_terminal_recipient` warning ("not durable after that terminal closes"). All addressing is **already terminal-handle-based, not backend-specific** — `to_handle`/`from_handle` never encode "claude" vs "codex".
- **This is entirely scoped to one `OrchestrationDb`, i.e. one local Orca process.** There is no cross-process/cross-host `MessageRow` exchange.
- `orchestration-federation.ts` (290 lines) is the closest thing to cross-host mail, but it is not a general mailbox: `orchestration.federationAttachStart` has the coordinator's host create/attach a worktree+terminal _on a remote host_ for one specific `dispatchId`, then call **that remote host's own** `runtime.sendTerminalAgentPrompt(...)` locally to seed the worker with a `buildDispatchPreamble(...)`. `orchestration-federation-control.ts` (`federationShow`/`federationRead`/`federationReadOutput`) lets the coordinator's host **poll** the remote worker's terminal output via RPC over the relay — it is host-to-host RPC observation of one dispatch, not a durable, addressable, many-to-many mailbox that spans hosts.
- Wire/opcode rules (`docs/reference/remote-wire-compatibility.md`): Rule 1 (new optional JSON field is free — decoders `.strip()`/ignore unknown keys), Rule 2 (**a new stream opcode is not safe** — unknown opcodes are silently dropped; must be capability-negotiated in the `Subscribe` handshake, precedent `SetOutputPaused` opcode 16: client advertises in `capabilities`, host echoes it on `subscribed`, client only sends after that echo), Rule 3 (changing _what_ the host publishes on an existing frame breaks old clients with no wire change at all — gate behind a capability the same way). Opcode numbers are enumerated and permanent in `src/shared/terminal-stream-protocol.ts:12-35` (`Ack=13, ClaimViewport=14, OutputSpan=15, SetOutputPaused=16, WriteUnavailable=17`). `src/shared/protocol-version.ts` — bump `RUNTIME_PROTOCOL_VERSION` only for removed methods/params or changed field meaning; new methods/fields never bump it.

## Tab-model change analysis

Making a tab = agent session (rather than tab = worktree-scoped-list-entry) touches:

- **Types**: `Tab` already carries `worktreeId` per-tab (`tab-types.ts:56`) — a tab is not structurally forced to belong to its group's worktree today, but every read path (`tabsByWorktree`, `unifiedTabs[worktreeId]`, `tabGroups[worktreeId]`) assumes the **outer key is the worktree**, and a session's identity is never first-class (no `sessionId` field on `Tab`; the closest is `structuredSessionId?: string`, which is Codex-specific TUI-adoption plumbing, not a general "this tab is session X" key).
- **Reducers**: every store slice under `src/renderer/src/store/slices/tabs/*` and `src/renderer/src/lib/workspace-session*.ts` keys off `worktreeId` as the outer map key (`tabsByWorktree`, `openFilesByWorktree`, `activeTabIdByWorktree`, etc. — a dozen+ parallel `Record<string, X[]>` maps in `workspace-session-state-types.ts`). Re-keying "tab" to session identity while workspaces still host many tabs means these maps need a second index (session→tab) or a flattened session-keyed store with worktree as a _field_, not a _key_ — a broad, mechanical but not conceptually hard change touching every one of those `*ByWorktree` maps.
- **`reconcileHydratedWorkspaceTabModels`** (the one hydration entry point) would need to reconcile by session id instead of/in addition to worktree id — currently it purely iterates `Object.keys(session.tabsByWorktree)`.
- **Persistence migration**: `WorkspaceSessionState` is a persisted, versioned blob (see `src/shared/workspace-session-schema.ts` and the migration files under `src/main/persistence/*`). Any structural change to how tabs are keyed needs a migration step alongside the existing legacy-field fallback pattern already used for `unifiedTabs` (comment at `workspace-session-state-types.ts:84-86`: "Read-path checks for this first; falls back to legacy fields if absent").
- **Status**: `AgentStatusEntry` (per-`paneKey`, i.e. per-pane-inside-a-tab) already has the pieces a "tab shows status" UI needs (`state`, `stateStartedAt`, `orchestration?`). No new type needed for status; it is a rendering/aggregation change (roll up pane statuses to a tab-level badge), not a schema change.
- **Cost**: nothing exists to attach yet (see above) — `alicornRunCost` must be built from `cloud/…/ledger.ts` `RunCostSchema` before a tab can show it. This is a hard dependency, not a UI-only task.

## Voice routing path

Current: `DictationController` → final transcript → `insertText()` → either a `dictation:insertText` DOM event consumed somewhere in the terminal pane (keystrokes into the PTY) or a direct paste/insertText into whatever text/contentEditable control has focus. No intent classification, no "send," no confirmation gate beyond the existing (terminal-only) `terminalConfirmBeforeInsert` setting.

VI1 ("voice intent → route transcripts to an agent holding the CLI skill … confirm before destructive") needs a new decision layer sitting between the final-transcript event and delivery:

1. Classify/route: decide which live agent session (paneKey/terminal handle) is "holding the CLI skill" — likely reusing the same `captureInsertionTarget()` notion of "the terminal that's focused," or a more deliberate targeting UI, since dictation today is purely focus-driven.
2. Deliver via `sendTerminalAgentPrompt(handle, prompt, options)` (`src/main/runtime/orca-runtime-controller-knows-pty-is-live.ts:124`) instead of `insertText`'s keystroke path — this submits a structured turn rather than typing raw characters, and it is already backend-neutral (works for any `TuiAgent`).
3. Confirmation gate: extend or generalize `VoiceSettings.terminalConfirmBeforeInsert` (`src/shared/speech-types.ts:75`) to gate the _destructive_ classification, not just "insert vs don't."

No sherpa-onnx/on-device-STT-specific gap was found — the STT pipeline (`src/main/speech/*`, `speech-runtime-service.ts`) already produces `SpeechTranscriptEvent{text, sessionId}` independent of destination; VI1 is purely a new consumer of that existing event, not a change to capture.

## Multi-repo primitives

- `Worktree.id = repoId::path` and `Repo` are both single-repo-scoped; nothing links two `Worktree`s as "one task, two repos" today.
- `ProjectGroup` is UI/sidebar-only (folder-scan grouping), carries no execution meaning.
- Orchestration dispatch's worktree selector is a single optional string (`coordinator-task-dispatch.ts:34,69`), and `orchestration-folder-worktree-placement.ts` validates against exactly one `repoSelector`.
- **MR1 ("repo/branch/worktree tuples") is new data model work**, not an extension of an existing array — there is no existing plural/array shape to widen. A "feature workspace" spanning repos would need: a new type (list of `{repoId, branch, worktreeId}`), a new coordinator entry point that resolves N worktrees instead of one, and UI (likely near `NewWorkspaceComposer*` and `ComposerParentWorktreePicker.tsx`) to pick multiple repos at creation time.

## Risks & open questions

- **Tab=session re-keying is the highest-risk item in UI1.** It touches ~12+ parallel `Record<worktreeId, X[]>` maps in `WorkspaceSessionState` plus every reducer that reads `tabsByWorktree`/`unifiedTabs`/`tabGroups` — a mechanical but wide blast radius, and it is a persisted-schema change requiring a migration path (legacy-field fallback, as already precedented for `unifiedTabs`).
- **UI1's "running cost per tab" cannot ship stand-alone** — it depends on a not-yet-built desktop consumer of `RunCost` from `@alicorn-cloud/control-plane-contract`, which itself depends on the Ledger API being reachable from the desktop (no existing wiring). Decompose as a separate, sequenced task, not folded into the tab-model change.
- **DESIGN-SYSTEM.md and prototype/tokens.css disagree** on scope (5 aliases vs. a full brand/avatar token set) and on theming convention (`.dark` class vs `data-theme` attribute). The plan must pick one; recommend the doc's narrower "Tokens" section as the actual UI4 diff and treat tokens.css as future-design reference only.
- **MB1 cross-host delivery model is undecided territory.** Federation today is "coordinator polls a remote worker it attached for one dispatch," not peer-to-peer mailbox. Whether MB1 generalizes federation's RPC-relay approach or introduces a new transport is an open design question this research cannot resolve from the code alone — flag for the plan author.
- **CR1 has no extraction tooling to build on** — first task is necessarily "pick an OpenAPI/TS-AST extraction approach," not "extend existing extraction," which likely raises its estimate risk beyond the quoted 4-6 ew (combined with CR2).
- **MR1 has zero existing multi-repo-per-task precedent** — even `ProjectGroup` (the closest concept) is purely a sidebar grouping. Confirm with the plan owner whether MR1's tuple type should live next to `Worktree`/`Task` types or as a new top-level "feature workspace" entity before scoping tasks.
