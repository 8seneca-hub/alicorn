New routes needed:

- **Control API**: `GET/PUT /v1/autonomy-policy` (or `/v1/projects/:projectId/stages/:stageKey/autonomy-policy` — tier 1 has no stage concept, so scope by `project_id` + a free-text `stageKey` default `'build'`, matching `step_outcomes.stage_key`'s own default). `policySet` must record `created_by` and reject `mode: 'never_gate'` without `expires_at` (ARCHITECTURE §9) — enforce with a zod `.refine`, same style as `ContextCaptureInputSchema`'s refine in `ledger.ts:54`.
- **Ledger API**: `GET /v1/ledger/evidence?memberId&stageKey&projectId` → `{ stats: member_stage_stats row, wouldDecide: <gate_reason if evaluated now> }`. Needs read access to the _policy_ to compute "what would decide now" — either (a) the Ledger API calls Control API server-to-server (adds a runtime coupling), or (b) `evidence` returns raw stats only and **main** combines them with the policy it already fetched, running the same `evaluateGate` pure function client-side. **(b) is cheaper and keeps the two services decoupled — recommended.**

`orchestration.policySet`/`policyGet`/`evidence` (main-process RPC, per ARCHITECTURE §8) are thin proxies: main's control-plane client (B2, unbuilt) calls Control API for policy CRUD and Ledger API for `/evidence`; `evaluateGate` itself is a **pure function** living in main (e.g. `src/main/alicorn/evaluate-gate.ts`) so `gateCreate`'s handler can call it synchronously without an RPC-inside-RPC.

## Export mechanics

- Generic export precedent: `src/preload/api/export-bridge.ts:4-11` (`exportApi.htmlToPdf`) → `src/main/ipc/export.ts:14-59` (`registerExportHandlers`, IPC channel `export:html-to-pdf`) → `htmlToPdf()` renders via Electron, then `dialog.showSaveDialog` + `writeFile`. Used today only for exporting markdown-editor content (`src/renderer/src/components/editor/export-active-markdown.ts`) — not signed, not ledger-related.
- **No signing primitive exists in ledger-api or control-api today** (`package.json` deps: only `hono`, `pg`, `zod`). Signing precedent lives in `cloud/apps/relay`: `nacl` (tweetnacl, ed25519) for host-pairing proofs (`relay-host-proof.ts:1`, `host-session-registry.ts:1,591` via `createHmac('sha256', ...)`), and `jose` (`^6.1.3`) for JWT verification in `admin-token-verifier.ts`/`relay-token-verifier.ts` (auth tokens, not export signatures).
- **Recommendation**: PV2's signed export should be produced **server-side** by the Ledger API (ARCHITECTURE §9: "Export is a first-class feature ... a signed, dated export"), using `node:crypto`'s `createHmac('sha256', secret)` over a canonical JSON serialization of the export payload + timestamp — no new dependency, matches the relay's existing HMAC pattern more closely than adding `tweetnacl` to a service that has no other need for asymmetric keys. Secret comes from a new env var (`ALICORN_EXPORT_SIGNING_SECRET`), read the same way `ALICORN_LOCAL_API_TOKEN` is (`config.ts` in each service).
- Desktop-side: a new Ledger API endpoint (e.g. `GET /v1/ledger/provenance/export?repoId&branch&format=json|md`) returns `{ payload, signature, signedAt }`; the desktop either (a) saves the raw JSON/Markdown via a new `export:save-text` IPC handler (same save-dialog shape as `export.ts`, but `writeFile(text)` instead of a PDF buffer), or (b) pipes the rendered Markdown through the existing `htmlToPdf` path for a PDF rendition. Either way this is a **new** main/preload surface — `export.ts` today only knows HTML→PDF.

## Constraints (ARCHITECTURE §7/§9 invariants, restated as checks)

- [ ] Hard stops (`always_gate`, `irreversible`, `inherited_cost=high`) are checked **before** any evidence/history lookup in `evaluateGate` — order in ARCHITECTURE §7 is fixed, accumulated runs must never suppress them.
- [ ] `reversibility`/`inherited_cost` are **read from stage/project config**, never inferred from the diff or the member's history. Tier 1 has no stages — GP1 must pick an explicit per-project authoring surface (extend `project_required_checks`-adjacent config) rather than guessing from file paths.
- [ ] `gateCreate{evaluate:true}` is the **only** place a caller can learn the policy's answer — no separate "should I gate?" query (§8). Any new `orchestration.evaluate`-only RPC would violate this; keep evaluation folded into `gateCreate`.
- [ ] Level 0 always gates and only **records** the decision it would have made (`gate_decision`/`gate_reason` on `step_outcomes`) — it must not skip the human at level 0 even if `evaluateGate` would say `auto`.
- [ ] `autonomy_policies.mode = 'never_gate'` **requires** `created_by` and a non-null `expires_at` — enforce in the zod schema (`.refine`), not just a DB constraint, so the RPC rejects it before any write.
- [ ] Blast-radius budgets are **per run**, not per task (§9) — `evidence.files`/`evidence.spend` must sum across every dispatch/task in the run, not reset per task, or splitting work launders past the limit.
- [ ] A member cannot loosen the required checks or the autonomy policy that judges it — `policySet`/required-checks authoring is an org-admin action, never callable by the dispatch being evaluated (mirrors `enforce_distinct_reviewer_backend`'s existing pattern).
- [ ] `member_stage_stats` is written **only** by the Ledger API's own insert path (`upsertMemberStageStats`, transactional with `insertStepOutcome`) — `evidence`/`policyGet` must be read-only against it from main's perspective.
- [ ] Windows are the **last 50 runs**, not lifetime, for demotion/promotion — any `evidence` read that returns "runs"/"accept_rate" from `member_stage_stats` as currently schemed is a **lifetime** running total (no windowing column), which does not match this requirement — see Risks.
- [ ] Export is signed and dated (§9) — treat any unsigned "copy as markdown" as a stopgap, not the PV2 deliverable.
- [ ] Additive wire changes only — `evaluate` on `gateCreate`, new `policySet/policyGet/evidence` methods, and new Ledger/Control API routes must all be optional/new-named, never change existing method behavior when the flag/field is absent.

## Risks & open questions

1. **`member_stage_stats` has no windowing.** The schema (`ledger-api/src/schema-sql.ts:46-52`) tracks lifetime `runs`/`accepted`/`accept_rate`, but ARCHITECTURE §7 demotion logic needs "last 50 runs" and "one rejected, or two amended within the last ten runs" — neither is derivable from the current aggregate. GP1/GP2 either need a windowed query over raw `step_outcomes` (more expensive, always correct) or a schema change to `member_stage_stats` (cheaper reads, needs a recompute-on-window-slide job). This should be resolved before writing `evaluateGate`'s `stats.recent_regression`/`stats.runs` checks.
2. **Corrections watcher (writes `human_verdict='amended'`) does not exist.** ARCHITECTURE §7: "Until the corrections watcher ships, advisory mode only." GP3 (level 1 advisory) is fine to build now, but any level-2/3 auto-accept logic in `evaluateGate` is explicitly out of scope until that watcher lands — confirm the plan only wires levels 0–1 (GP3 says exactly this) and that `accept_rate` inputs are understood as provisional (no amendment signal yet, only succeeded/failed outcome).
3. **No stage concept in tier 1** — `reversibility`/`inherited_cost`/`required_checks` are architecturally stage-scoped but tier 1 has no `stages` table. The desktop plan's precedent (`project_required_checks`, per-project not per-stage) is the honest tier-1 scoping; GP1's policy table needs the same per-project fallback, with `stage_key` as a free-text default-`'build'` dimension mirroring `step_outcomes.stage_key`, not a real FK.
4. **Dependency chain risk**: GP1 (`evaluateGate`) needs live `member_stage_stats`/`step_verifications`, which need C2/C3/D5 (outbox enqueue, drainer, diff coverage) — **none of which are built**. Sequencing GP1 before the base ledger-write pipeline exists means `evaluate:true` can only ever return `unverified`/`history` gates (no real data flows in) until that plumbing lands. Recommend either building C2/C3 first (as a shared dependency) or explicitly scoping GP1's first cut to work correctly with all-empty evidence (fails safe: always gates) and adding a follow-up task once C2/C3 ship.
5. **Self-reported `filesModified` vs. blast radius.** Using the agent's own `--files-modified` claim as `evidence.files` for BR1 is gameable — an agent could under-report. Recommend BR1 compute files-changed via `git diff --name-only <baseRef>...HEAD` against the worktree (same approach D5 uses for diff coverage) rather than trusting the settlement payload, at least for gates opened after settlement; a gate opened _mid-task_ (before any diff exists) cannot check blast radius at all except against live worktree state.
6. **Protected paths have no config surface anywhere.** Needs a net-new project-scoped list (glob patterns?) in Control API, plus a matcher in main — fully greenfield, no existing "denylist" code to extend.
7. **PV2 signing key custody.** An HMAC secret shared between ledger-api instances is simplest but means anyone with the secret can forge an export; if auditors need non-repudiation (a specific person's signature, not just "the service's"), an asymmetric scheme (ed25519 via `node:crypto` or `tweetnacl`, matching relay's existing choice) is worth the extra complexity. Confirm with the PR-body/export requirement's actual audience before choosing.
8. **`gateCreate`'s `evaluate` flag and required-checks are inherently post-hoc for anything opened before task completion.** Confirm the intended flow is: gates opened as part of a stage/task-transition (after `worker_done` settles, before the _next_ stage's dispatch) — not gates opened by an in-flight agent mid-task — because only the former can honestly answer "did required checks pass."
