## Wire contract the desktop expects

| Endpoint (desktop config field) | Method | Request body | Response the desktop parses |
|---|---|---|---|
| `authorizeEndpoint` (default `{authBaseUrl}/v1/desktop/auth/authorize`, override via `ORCA_CLOUD_AUTHORIZE_URL`) | browser GET (via `shell.openExternal`) | query params: `client_id, response_type=code, redirect_uri, scope, nonce, state, code_challenge, code_challenge_method=S256, local_profile_id` | n/a — browser redirect; must land back on `redirect_uri` with `?code=&state=` |
| `sessionEndpoint` (`/v1/desktop/auth/session`) | POST | `{ code, codeVerifier, nonce, redirectUri, state, localProfileId }` | `{ accessToken, refreshToken, expiresAt, cloud: {cloudProfileId, userId, email, displayName?, activeOrgId?, activeOrgName?, linkedAt}, organizations?: [{orgId,name,role?}], capabilities: {flags, refreshedAt} }` |
| `refreshEndpoint` (`/v1/desktop/auth/refresh`) | POST, 60s timeout | `{ refreshToken }` | same shape as session |
| `capabilitiesEndpoint` (`/v1/desktop/auth/capabilities`) | POST, `Authorization: Bearer <accessToken>` | `{}` | `{ cloud?, organizations?, capabilities }` (cloud/organizations optional here) |
| `profileEndpoint` (`/v1/desktop/auth/profile`) | POST, bearer | `{ orgId?, name? }` | full session-exchange shape (creates a new cloud-linked local profile scoped to an org) |
| `orgEndpoint` (`/v1/desktop/auth/org`) | POST, bearer | `{ orgId }` | `{ cloud, organizations?, capabilities }` (switches active org) |
| `logoutEndpoint` (`/v1/desktop/auth/logout`) | POST, bearer | `{ refreshToken }` | (ignored/void) |
| `relayTokenEndpoint` (`/v1/desktop/auth/relay-token`) | POST, bearer | `{ relayHostId, hostPublicKeyB64 }` | `{ relayToken, expiresAt }` (zod `RelayTokenResponseSchema.strict()` in `relay-http-client.ts`) |

The plan's I2 lists broker endpoints as `{session,refresh,capabilities,org,logout}` — **`authorize` is deliberately absent**. That means `ORCA_CLOUD_AUTHORIZE_URL` must be pointed directly at Keycloak's own authorize endpoint (not through Control API), since the default construction (`{authBaseUrl}/v1/desktop/auth/authorize`) would 404 against a Control API that never implements that route. See Risks.

All non-authorize normalizers require every field they read to be present with the right primitive type or they throw (`assertString`/`assertNumber`) — a broker response missing `expiresAt` or `cloud.userId` fails closed, not softly.

## Risks & open questions

1. **Loopback redirect confirmed**: `profile-cloud-pkce.ts:128` builds `redirectUri = http://127.0.0.1:${address.port}/auth/callback` — a random ephemeral port, fixed path. Keycloak's redirect-URI matching must be configured to accept `http://127.0.0.1:*/auth/callback` (Keycloak matches loopback URIs ignoring port per RFC 8252 — needs verifying against the actual Keycloak 26 admin console redirect-URI-pattern behavior, since some IdPs require an explicit wildcard glob like `http://127.0.0.1:*/auth/callback` while others need `http://127.0.0.1/auth/callback` prefix matching — **verify by hand during I1**, don't assume from the RFC alone).
2. **`ORCA_CLOUD_AUTHORIZE_URL` must bypass the Control API broker.** I2's endpoint list omits `/v1/desktop/auth/authorize`. If `ORCA_CLOUD_AUTHORIZE_URL` is left unset, the desktop computes `endpoint(authBaseUrl, '/v1/desktop/auth/authorize')` and calls a route the Control API never implements. The desktop.env.example (and any Keycloak-mode docs) must set `ORCA_CLOUD_AUTHORIZE_URL` directly to Keycloak's realm authorize endpoint (e.g. `http://127.0.0.1:8080/realms/alicorn/protocol/openid-connect/auth`). Confirm this is the intended shape before writing I2 — the alternative (Control API proxies/redirects `/authorize` too) is also structurally possible but contradicts the plan's endpoint list.
3. **Token exchange must still go through the Control API**, not directly to Keycloak's token endpoint, because `sessionEndpoint`'s request body (`{code, codeVerifier, nonce, redirectUri, state, localProfileId}`) is Orca's own shape, not OAuth2's (`grant_type`, `client_id`, etc.), and the response (`{accessToken, refreshToken, expiresAt, cloud, organizations, capabilities}`) requires Control-API-side enrichment (`cloud.*`, `capabilities.flags`) that Keycloak's token endpoint cannot produce on its own. This means: **the `accessToken` handed back to the desktop should be the raw Keycloak-issued access token** (so `requireTenant`'s keycloak-mode JWKS verification — issuer + `azp` — works directly against it later), while `cloud`/`organizations`/`capabilities` are Control-API-computed side data returned alongside it. Verify this is achievable: Keycloak's token response nests `access_token` as an opaque-looking (but actually JWT) string; the Control API's `/session` handler is a thin broker that calls Keycloak's `/token` endpoint server-to-server, then re-shapes the response — it must NOT mint its own token for `accessToken`, or the relay/Control-API JWKS verification story breaks.
4. **`organization` claim shape from Keycloak 26 is unverified in this codebase** — ARCHITECTURE §5 asserts "tenant id = Keycloak organisation id, proven by the token's `organization` claim," but the exact JSON shape of that claim (single org id string vs. an object keyed by org alias, as Keycloak's Organizations feature typically emits) is not present anywhere in this repo. This needs to be confirmed empirically against a real Keycloak 26 token during I1/I2 rather than assumed from memory.
5. **Refresh-token rotation + "ambiguous failure" handling in `profile-cloud-session-refresh.ts` is already built for a broker that owns a single non-rotating-until-refreshed pair.** If Keycloak enforces stricter refresh-token-reuse-detection semantics than whatever tier-1's (still hypothetical) session broker currently assumes, the existing single-flight + replay-guard logic (`profile-cloud-refresh-replay-guard.ts`) should still hold since it treats "no clean status line" as ambiguous and never assumes success — but confirm Keycloak's realm refresh-token settings (rotation on/off, reuse detection) are configured consistently with what the Control API broker promises the desktop.
6. **`capabilities.flags` consumer found**: only one real consumer exists today — `src/main/runtime/relay/relay-auth-context.ts:32`, `relayEntitled: session.session.capabilities.flags['relay.use'] === true`. The Control API's `/capabilities` broker route must at minimum be able to emit `{ flags: { 'relay.use': true } }` for a signed-in user, or relay access silently breaks for every Keycloak-mode user.
7. **Keycloak's own Postgres schema/role is not yet provisioned.** `cloud/dev/compose/postgres-init/01-alicorn-app-role.sql` only creates `alicorn_app` owning `control`/`ledger` schemas. The plan's suggested `KC_DB_SCHEMA=keycloak` needs either its own role+schema statement added to that init script or Keycloak given its own Postgres user — decide and add before I1's compose change, since `01-alicorn-app-role.sql` runs once at first container init (`docker-entrypoint-initdb.d`), so a later manual `ALTER`/`CREATE SCHEMA` would not survive a fresh volume.
8. **B1 (desktop `readAlicornBearer`) is unbuilt.** I4 either waits on the desktop-plan owner to land B1 first (its local-mode body is trivial and unblocks I2/I3 testing independently), or this plan's I4 builds the file itself. Either way, coordinate — two people writing `src/main/alicorn/control-plane-session.ts` from different plans is a guaranteed merge conflict.
9. **Production defaults are Orca-branded** (`PRODUCTION_API_BASE_URL = 'https://login.alicorn.8seneca.com'`, `PRODUCTION_CLIENT_ID = 'orca-desktop'` in `profile-cloud-auth-config.ts:19-20`). Per CLAUDE.md, do not rename these piecemeal — they're in scope for the rebrand sweep, not this plan. Dev/local Keycloak mode only needs the env-var overrides (`ORCA_CLOUD_API_URL`, `ORCA_CLOUD_CLIENT_ID`, `ORCA_CLOUD_AUTHORIZE_URL`, etc.), all already unpacked correctly for non-packaged builds.
