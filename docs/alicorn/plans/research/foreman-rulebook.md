# Foreman core + Rulebook — plan research

Codegraph was not initialized for this worktree (`.codegraph/` absent in the worktree and the main
repo) — this research used `Bash`/`Read`/`grep` directly instead.

## 1 · Coordinator today vs Foreman target (gap table)

Orca already has a working orchestrator-subagent loop — `Coordinator`
(`src/main/runtime/orchestration/coordinator.ts:38-317`). It dispatches worker *terminals* (not
Claude Code Agent-tool subagents) via CLI messages over the existing `orchestration.*` RPC surface.
**This is the substrate FM1-4 extends** — Foreman is not a new engine, it is stricter rules layered
on this one, plus a few new fields.

| Capability | Coordinator today | Foreman target (FM1-4) | Gap |
|---|---|---|---|
| Run loop / DAG convergence | `executeLoop`/`tick` (`coordinator.ts:94-166`), `evaluateDagConvergence` (`coordinator-dag-convergence.ts:6-32`) | same | none — reuse as-is |
| Dispatch pre-flight (stale base, circuit breaker) | `dispatchTaskToWorker` (`coordinator-task-dispatch.ts:62-161`), `coordinator-stale-base-flag.ts` | same | none |
| Escalation triage | `applyEscalationToDispatch` (`coordinator-escalation-triage.ts:6-67`) — circuit-breaks after 3 failures | same, plus D4's context-ceiling *offer* (separate mechanism, see §6) | D4 is a new watcher, not an Coordinator change |
| Decision gates | `openDecisionGateFromMessage`/`reblockTasksWithPendingGates` (`coordinator-decision-gates.ts:6-62`) — human-only resolution | same | none |
| Nested dispatch depth | `NESTED_WORKER_MAX_DEPTH_DEFAULT = 1` (`src/shared/nested-worker-depth.ts:8`); `buildSubDispatchSection` lets a worker sub-dispatch when `depth < maxDepth` (`preamble.ts:117,201-219`) | Foreman's lead ↔ subagent relationship *is* this depth-1→2 pattern | AT1 (v2.0, agent-composed teams) needs deeper/typed nesting; not tier-1 |
| **Journal on disk (FM1)** | none — state lives only in SQLite (`OrchestrationDb`) and Coordinator's in-memory `CoordinatorState` (`coordinator.ts:27-33`) | `.foreman/<task-id>/journal.md`, resumable | **new**: no persistence of plan/decisions/assumptions/contract-registry today |
| **Bounded report (FM2)** | `worker_done --body` is a *convention* (preamble tells the worker "3-sentence summary", `preamble.ts:75-79`), never enforced; no size cap anywhere in the send path | ≤1500-token schema enforced at the tool boundary, overflow → file + path | **new**: see §2 |
| **Lead restrictions (FM3)** | none — any dispatched agent can Edit/Write | lead writes no code, reads no implementation, ≤40% window ceiling | **new**: see §3 |
| **Run view + cost meter (FM4)** | Coordinator has no cost/context visibility; per-turn token usage is parsed elsewhere (`transcript-record-parser.ts`) but not surfaced per-run | live cost meter | **new** desktop UI + wiring; ledger-side cost columns already exist (`step_outcomes.spend_cents`, `usage` — `cloud/apps/ledger-api/src/schema-sql.ts:14`) |
| `execution_strategy` field | not present on `tasks` | task-level `single`/`orchestrated`, escalation offer | **planned, not yet built** — `docs/alicorn/plans/2026-09-06-tier-1-desktop.md` Task 10 (D1) and Task 13 (D4); `src/main/alicorn/` does not exist yet (confirmed empty) |

**Key implication:** Foreman's "lead" role, in the product (not the `/foreman` prototype), is most
naturally a `Coordinator` instance whose *dispatched workers* are worker terminals running under
`execution_strategy: orchestrated`. FM2/FM3 are constraints added to the existing
`dispatchTaskToWorker` → `buildDispatchPreamble` → `worker_done` round-trip, not a parallel system.

## 2 · Report protocol enforcement points

No layer in the current worker_done path enforces a size limit:

- **RPC schema** — `SendParams.body` is `OptionalString` (`src/main/runtime/rpc/methods/orchestration-schemas.ts:97-116`), and `OptionalString` (`src/main/runtime/rpc/schemas.ts:27-31`) only checks `typeof === 'string' && length > 0` — no `.max()`.
- **CLI flag parsing** — `getOptionalStructuredMessagePayload` (`src/cli/handlers/orchestration/message-payload.ts:4-60`) reads `--body`/`--report-path` as raw strings and stashes `reportPath` into the JSON payload verbatim (line 53-55); no read of the file, no length check.
- **CLI handler** — `'orchestration send'` (`src/cli/handlers/orchestration/message-send-handler.ts:61-137`) passes `body` straight into `sendParams` (line 91) with no inspection.
- **Federated (remote/SSH) path** — `parseFederatedWorkerReportPayload` (`src/main/runtime/orchestration/federation-worker-report-payload.ts:4-37`) validates only `taskId`/`dispatchId`/`outcome` shape, same gap.
- **Settlement** — `settleWorkerReportInTransaction` (`src/main/runtime/orchestration/db/dispatch-context/worker-report-settlement.ts:27-176`) stores `result` (the whole JSON including `body`) unbounded on the task/dispatch row.

**Existing precedent for "cap at ingest"** (a good pattern to copy, different subsystem): `capOpenCodeHookText` in `src/shared/agent-hook-listener/listener-limits.ts:14-18` truncates a different channel's text at `OPENCODE_HOOK_TEXT_MAX_CHARS = 8_000` chars, with a comment explaining why (O(n²) growth risk). FM2 wants the same shape — a named constant + a cap function — but keyed to *tokens*, not chars, and with overflow-to-file instead of truncation (truncation would silently drop the `open_questions`/`interface_delta` tail).

**No tokenizer exists in this codebase.** `grep` for `tiktoken`/`gpt-tokenizer` found nothing in `package.json`, and no `estimateTokens`/`countTokens` utility exists outside of already-recorded usage numbers (`src/main/automations/hermes-cron-output.ts:265-267`, which sums *actual* API `input_tokens`/`output_tokens`, not a text estimator). A char/4 heuristic or a small tokenizer dependency will be needed for the ≤1500-token check — flag as an open question (§9).

**Where to add enforcement:** the CLI handler (`message-send-handler.ts`, `'orchestration send'`) is the closest analog to "the tool boundary" FM2 names — it is the last synchronous point before the RPC call, mirrors where `getOptionalStructuredMessagePayload` already builds `reportPath`, and matches the CLAUDE.md language ("enforced at the tool boundary"). Add a size check there for `type === 'worker_done'`: if `--body` exceeds the ceiling, either reject with the exact message the preamble should teach (`buildDispatchPreamble` in `preamble.ts:75-79` already says "3-sentence summary" — tighten to instruct the ceiling and the `--report-path` escape hatch) or auto-spill the overflow to a file and rewrite `payload.reportPath`. A second, server-side check in `SendParams`/`reconcileWorkerDoneMessage` (`lifecycle-reconciliation.ts:174-305`) is worth adding as defense-in-depth since the federated/SSH path bypasses the local CLI handler entirely.

## 3 · Lead restrictions feasibility

**"Writes no code, reads no implementation" is not mechanically enforced anywhere today** — it is
purely a prompt convention in `.claude/commands/foreman.md:35-39` ("Write no code... Read no
implementation"). Investigation of what Orca *could* use:

- `agent-trust-presets.ts` (`src/main/agent-trust-presets.ts`) is **not** about permission modes — it only pre-marks a workspace as trusted for cursor-agent/Copilot/Codex's own "trust this folder?" menus. A red herring for tool restriction; noted so a future implementer doesn't chase it.
- **Dynamic permission mode exists mid-session**: `setClaudeStructuredOption` (`src/main/claude/claude-structured-options.ts:35-120`) calls `session.connection.setPermissionMode(input.value as PermissionMode, ...)` (line 44) against the Claude Agent SDK. `PermissionMode` (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:2238`) is `'default' | 'acceptEdits' | 'bypassPermissions' | 'plan' | 'dontAsk' | 'auto'` — none of these is a hard "no Edit/Write" mode; `'plan'` is the closest (blocks execution, not just edits) but is a *planning* mode, not a permanent restriction, and is user-facing (Orca's `PermissionMode` type, `src/main/claude/hook-settings.ts` etc., doesn't wire an orchestration-specific override of this today).
- **`disallowedTools`/`allowedTools` exist at SDK launch-option level** (`sdk.d.ts:1444,1464` — string arrays passed into the session's `Options`), but **Orca does not currently wire these anywhere** — the only in-repo reference is a CLI-passthrough test fixture (`src/shared/agent-resume-launch-command.test.ts:245-249`, a user-typed `--allowedTools` flag on `claude --resume`, unrelated to orchestration). This is the most promising enforcement lever: a Foreman lead's launch (worker-start/dispatch options, `orchestration-worker-start-schema.ts` per the D2 plan) could set `disallowedTools: ['Edit', 'Write', 'NotebookEdit', ...]` when a task is the orchestrating stage. It is a launch-time-only knob (no evidence it can be changed mid-session the way `permissionMode` can).
- **PreToolUse hooks exist but are informational only.** `CLAUDE_EVENTS` in `src/main/claude/hook-settings.ts:36-100` registers `PreToolUse` (line 74-79) purely to feed a live dashboard readout (tool name + input preview) — the managed hook command is not built to return a deny decision. Claude Code's hook protocol *does* support a PreToolUse hook returning a block/deny verdict (general SDK capability), but Orca's installer never exercises that path; wiring a deny-capable PreToolUse hook scoped to one pane/session would be new plumbing, and is the mechanism PROJECT-BRIEF §07 calls **QA1 "tool-level enforcement, not a prompt rule"** (v2.0, 2-3ew) — the same primitive FM3 needs for the lead. Worth building once and sharing between FM3 and QA1 rather than twice.

**Feasible path for FM3, ranked:** (1) `disallowedTools` at dispatch/launch time — cheapest, no new hook plumbing, but is advisory the same way `allowedTools` is (a determined agent can still be told to ignore it in-context; SDK-level enforcement quality needs verification against the installed SDK version). (2) A deny-capable `PreToolUse` hook scoped by pane/session — stronger, reusable for QA1, more work. Tier-1/FM3 should probably ship (1) and note (2) as the QA1-shared follow-up, matching "guard rails ship with the feature that needs them" (CLAUDE.md:113).

## 4 · Context-window accounting for the ≤40% ceiling

The desktop tier-1 plan already designs the primitive FM3 needs, for a different consumer (D4's
escalation offer, `docs/alicorn/plans/2026-09-06-tier-1-desktop.md` Task 13, "D4"):

- `contextTokensFromTranscriptTail(text: string): number | null` — scans a transcript tail backwards for the last parseable assistant record via `parseClaudeUsageRecord` (`src/main/claude-usage/transcript-record-parser.ts:175-178`, which sums `input_tokens + output_tokens + cache_read_input_tokens + cache_creation_input_tokens` per turn, see fields at lines 21-31) and returns `inputTokens + cacheReadTokens + cacheWriteTokens` for the latest turn — a good proxy for "how much context this session is currently carrying."
- `readTranscriptTail(path, maxBytes=256KB)` — cheap tail read, no full-file rescan.
- D4's ceiling is `ALICORN_CONTEXT_CEILING_TOKENS = 300_000` (absolute); FM3's is "≤40% of window" (relative to the *model's* context window, e.g. ~80k of 200k for Sonnet). **None of `transcript-context-tail.ts`, `context-ceiling-watcher.ts`, or `src/shared/alicorn/context-ceiling.ts` exist yet** — confirmed `src/main/alicorn/` is empty in this worktree. FM3 should reuse `contextTokensFromTranscriptTail` (once D4 lands it) with a different, percentage-based ceiling function rather than re-deriving the same tail-parsing logic — literally the same file, parameterized threshold.
- `PreCompact`/`PostCompact` are already registered Claude hook events (`hook-settings.ts:92-99`) — `PreCompact` is deliberately *not* wired (comment explains: fires before compact is validated, would wrongly mark the pane "working"), but `PostCompact` is. This is the natural signal for "the lead just compacted into its journal" if FM3 wants to react to a compaction rather than only pre-empt one.

## 5 · The `/foreman` prototype — journal/report seed

Full templates already exist and are ready to lift into FM1/FM2's schema:

- **Journal** (`docs/alicorn/foreman-templates.md:98-145`): `.foreman/<task-id>/journal.md`, sections `Status/Started/Budget/Spent so far`, `Objective`, `Decisions` table (`#|Decision|Chosen|Why|Reversible?`), `Assumptions made without asking` table (`#|Assumption|Blast radius|Nodes depending on it`), `Plan` table (`Node|Owner|Depends on|Status|Model`), `Contract registry` (freeform, accumulated interface deltas), `Log` (timestamped line items), `Not done, and why`.
- **Report schema** (`foreman-templates.md:57-92`): YAML with `status: done|blocked|needs_decision|failed`, `summary` (≤3 sentences), `changes[]` (`repo/path/kind/why`, paths only — never file contents), `interface_delta[]` (`kind/name/shape/breaking`), `verification` (`command/result/evidence`), `open_questions[]`, `artifacts[]` (paths for anything too long), `cost` (`tokens_in/tokens_out`). This is a near-literal match for CLAUDE.md's FM2 field list.
- **Subagent brief template** (`foreman-templates.md:7-41`): `Objective / Scope / Boundaries / Contract you build against / Verification / Report back` — the shape a Coordinator-issued task spec (`buildDispatchPreamble`'s `taskSpec`, `preamble.ts:150-151`) would need to carry when `execution_strategy: orchestrated`.
- **Compaction rule** (`foreman-templates.md:149-156`): "when context approaches ~40%, write everything to the journal, then continue reading only the journal" — this is FM3's ≤40% ceiling stated operationally; the test given ("if this session died right now, could a fresh lead pick up from the file alone?") is a good acceptance criterion for FM1.
- **`.foreman/` does not currently exist in this worktree** (it's gitignored, `.gitignore:177`, and only ever created at runtime by the slash command) — confirm with a fresh `/foreman` run before assuming any concrete example files exist to mine further.
- The command file itself (`.claude/commands/foreman.md:1-169`) is the process spec: ambiguity sweep once at the start (§1, lines 48-61), plan+journal (§2), dispatch rules — four required brief sections, parallel dispatch of independent work (§3, lines 72-96), bounded reports (§4), cross-model review that ends on "no new findings" with a 3-round budget (§5, lines 101-109), discard-not-correct on subagent failure (§6, lines 111-118), and a run report as the close-out (§7, lines 120-131) — "If the work produced a pull request, this is its body," which is the literal PR-body/provenance tie-in from PROJECT-BRIEF §06.

## 6 · Rulebook (RB1) data flow

- **`members.system_rules` already exists** as the extension point: contract type `MemberInputSchema.systemRules: z.string().max(20_000).default('')` (`cloud/packages/control-plane-contract/src/member.ts:17`), column `system_rules TEXT NOT NULL DEFAULT ''` (`cloud/apps/control-api/src/schema-sql.ts:13`). It is a single free-text blob per member, not a structured/append-only rule list.
- **Write path is whole-object replace, not append.** `updateMember` (`cloud/apps/control-api/src/members-repository.ts:93-105`) does `UPDATE members SET ... system_rules = $6 ...` from a full `MemberInput`; the REST route is `PUT /v1/members/:id` (`cloud/apps/control-api/src/members-routes.ts:48-64`), always re-validated by `MemberInputSchema.safeParse` against the whole payload. **There is no PATCH/append endpoint.** An "accept proposed rule" flow must read the member, append the new rule text to the existing `systemRules` string client-side, and PUT the whole member back — or a new endpoint must be added. Given "Interface decisions... Reuse Before Reimplementing" (AGENTS.md), reusing the existing PUT with a read-modify-write is the lower-risk path for RB1 unless concurrent-edit races become a real problem (two proposals accepted near-simultaneously could clobber each other — worth a test).
- **Amendment input already has a column, no watcher yet.** `step_outcomes.human_verdict TEXT CHECK (... IN ('accepted','rejected','amended'))` exists (`cloud/apps/ledger-api/src/schema-sql.ts:17`), plus `amended_after_ms` (line 18). But `grep` across the repo found **no corrections-watcher implementation** anywhere (only this schema column) — RB1 depends on that watcher (out of this research's scope; PROJECT-BRIEF §06 frames it as "already the Rulebook's input" but it does not exist yet either). RB1's design must not assume the watcher is built; it should specify RB1's own consumption contract (what shape of "amendment event" it expects) so the watcher can be built to match.
- **No PATCH exists yet for `human_verdict` on an already-posted `step_outcomes` row** — `ledger-routes.ts` only has `POST /v1/ledger/step-outcomes` (create) and `PATCH .../spend` (line 27); a corrections watcher marking a row `amended` after the fact needs a new PATCH route or the watcher must be the one to set `human_verdict` at initial post time (unlikely, since corrections happen after settlement). Flag as a cross-cutting gap for whoever builds the watcher, and as a dependency RB1 should state explicitly rather than assume.
- **`member_stage_stats`** (`cloud/apps/ledger-api/src/schema-sql.ts:46-51`, fields `runs/accepted/accept_rate/last_amended_at/level`) is the existing demotion mechanism PROJECT-BRIEF §06 references ("that event costs a member a level"). RB1 is explicitly a *second* consumer of the same amendment event — it should not duplicate the read of `step_outcomes.human_verdict`, it should sit alongside whatever demotion logic already (will) read it.
- **How rules reach the agent (dispatch preamble vs. worktree file)** — no existing per-member "system prompt" injection was found in the dispatch path. `buildDispatchPreamble` (`preamble.ts:49-152`) builds a fixed CLI-instructions text; it has no member-aware section today (Task 11/D2, not yet built, plans to attach a `dispatchMember` to the dispatch context but doesn't mention injecting `systemRules` into the preamble). Two plausible mechanisms, neither built: (a) append `systemRules` as a preamble section, mirroring `buildDriftSection`/`buildSubDispatchSection`'s pattern (`preamble.ts:221-234`, `201-219`) of a fenced, conditionally-included block; (b) write a CLAUDE.md-style file into the worktree before dispatch (heavier — touches the working tree, has to be cleaned up, and conflicts with Orca's "don't mutate the workspace on the user's behalf" instincts elsewhere). (a) is simpler and consistent with how Orca already teaches workers everything else — recommend it.
- **"Committed to the repo" (git commit from main)** — no existing pattern found for "main process auto-commits a generated file". Plenty of `gitExecFileAsync` call sites exist (`src/main/repo-git-remote-identity.ts`, `src/main/runtime/runtime-worktree-create-git.ts`, etc.) but all for read-only/worktree-lifecycle operations, none for authoring a commit on the user's behalf. RB1 will need new code following AGENTS.md's Git Binary Compatibility conventions (baseline Git 2.25, `GitCapabilityCache`, host-scoped capability state for native/WSL/SSH) — and per the SSH Use Case doc, must consider that the repo whose rules are being committed may be on a remote/SSH host, not local.
- **UI surface** — "Members pane" and "B4" are named in CLAUDE.md/the desktop plan (Task 4, "B4: Members settings pane") as the existing settings surface; an "accept proposed rule" affordance is a natural addition there, but that pane is also not yet built in this worktree (only `Task 4 (B4)` planned, not confirmed implemented — verify before assuming it exists).

## 9 · Constraints (CLAUDE.md invariants, restated for this scope)

- **Foreman is an add-on** — every FM1-4 change must leave `Coordinator`/`orchestration.*` working with no `orchestrated`-strategy tasks in flight; do not make single-agent dispatch depend on the journal, the report schema, or the lead's tool restrictions.
- **Lead writes no code, reads no implementation** (CLAUDE.md:80) — a hard product rule, currently zero-enforced (see §3); FM3 must close that gap, not merely restate the prompt convention already in `.claude/commands/foreman.md`.
- **Returns are schema-bounded with a hard token ceiling; overflow → file + path, enforced not advised** (CLAUDE.md:82) — "enforced" is the operative word; a prompt instruction (what exists today, `preamble.ts:75-79`) does not satisfy this.
- **State is on disk (Feature Journal)** (CLAUDE.md:84) — FM1's journal is that state; it must be the thing a resumed Foreman run reads, not a cache reconstructed from Coordinator's SQLite alone (SQLite has tasks/dispatches, not decisions/assumptions/contract deltas).
- **A member cannot loosen its own criteria** (CLAUDE.md:111) — relevant to RB1: an amendment proposes a rule *on* the member that caused the correction; the accept step must be a human action (or another member's authority), never the same member self-approving its own rule.
- **Guard rails ship with the feature that needs them** (CLAUDE.md:113) — FM3's tool restriction and QA1's sandbox are the same primitive (§3); shipping FM3 without at least a `disallowedTools` guard would violate this.
- **Autonomy is unlocked by evidence, evidence only accumulates by running gated** (CLAUDE.md:115) — RB1's amendment→rule flow must go through a human-accept gate (per the plan's own framing: "human accepts"); do not auto-commit a proposed rule without that gate.
- **`tenant_id` on every row, RLS forced** — already true for `members`, `step_outcomes`, etc. (confirmed: every table in both schema-sql.ts files carries `tenant_id` + `tenantRlsPolicySql(...)`); any new RB1 table (e.g., a rule-proposal queue, if the design needs one beyond the read-modify-write PUT) must follow the same shape.

## 10 · Risks & open questions

1. **No tokenizer in this codebase.** FM2's ≤1500-token ceiling needs either a cheap heuristic (chars/4) or a small dependency; a heuristic risks both false rejections (verbose but compliant reports) and false acceptances (dense JSON that's token-heavy per char). Decide before implementing the CLI-side check.
2. **`disallowedTools` enforcement strength is unverified.** No test in this repo exercises it; before relying on it for FM3, verify against the installed `@anthropic-ai/claude-agent-sdk` version whether a determined agent can still invoke a disallowed tool (e.g., via Bash shelling out) — if so, FM3 needs the PreToolUse-deny-hook path (heavier) from day one, not as a stretch goal.
3. **PUT-only member update risks a lost-update race** for RB1's accept flow (two proposals, or a proposal racing an unrelated member edit, could clobber each other's `systemRules`). Needs either an `updated_at`-based optimistic-concurrency check on `PUT /v1/members/:id`, or a small append-only "rule proposals" table feeding a server-side append instead of a client-side read-modify-write.
4. **The corrections watcher does not exist.** RB1 cannot be built end-to-end without it; scope RB1's plan to (a) the accept-UI + member-write half, and (b) a clearly-specified input contract, and treat the watcher itself as a shared dependency with whatever demotes `member_stage_stats.level` — do not silently build a second, incompatible watcher.
5. **No PATCH exists for `human_verdict` on a settled `step_outcomes` row** — either the watcher needs a new Ledger-API route, or ledger writes need to defer initial posting until the correction window closes (unlikely, breaks "exactly-once… server time orders everything"). Flag for whoever scopes the watcher.
6. **`.foreman/` prototype has no committed example run** in this worktree — before treating the templates as final, run `/foreman` once on a real task and diff what it actually produces against `docs/alicorn/foreman-templates.md`, since CLAUDE.md explicitly asks for that feedback loop ("feed what breaks back into the design").
7. **Foreman-as-Coordinator vs. Foreman-as-Claude-subagents is an open design decision this research surfaced but did not see resolved anywhere in the docs.** The `/foreman` slash command prototype uses Claude Code's native Agent/Task tool (in-session subagents); the product plan (tier-1 desktop, `execution_strategy`) implies Foreman dispatches via Orca's own orchestration RPC (worker terminals). These are different mechanisms with different report boundaries (Claude's tool-result channel vs. `orchestration send --type worker_done`). FM1-4's task decomposition below assumes the **product** target is the orchestration-RPC mechanism (matches "runs when `execution_strategy = orchestrated`", CLAUDE.md, and Task 10/13 of the desktop plan) — surface this assumption to the plan author explicitly.
