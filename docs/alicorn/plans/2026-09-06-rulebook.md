> **Caveat (v1.5):** depends on the corrections watcher (ledger-completion plan) and the Members pane (B4). Re-verify anchors when picking up.

**Goal:** An amendment is a finding a human paid for by hand. The same event that demotes a member proposes a standing rule on that member; a human accepts or rejects it; an accepted rule is appended to the member's `system_rules` server-side, reaches the member in every later dispatch preamble, and is committed to the repo as `.alicorn/rules/<member>.md`.

**Architecture:** The corrections watcher already enqueues `human_verdict_patch` items; this plan adds a second consumer: when the drainer posts an `amended`/`rejected` verdict it also posts a **rule proposal** (Control API, `rule_proposals` table, `pending`, with the amendment context — commit sha, files, a diff excerpt ≤ 4 KB). The Members pane lists pending proposals; the human writes/edits the rule text and accepts. Acceptance is a server-side **append** (`POST /v1/members/:id/rules`) — no read-modify-write of the whole member — and main then writes the rule file into the project's primary worktree and commits it when the tree is clean.

**Spec:** `docs/alicorn/PROJECT-BRIEF.md` §05 (Rulebook), §06.2, §11.3; `CLAUDE.md` decision 3; ledger-completion plan (verdict source); `docs/alicorn/GRAPH-ENGINEERING.md` (the Rulebook is the learning edge); research `research/foreman-rulebook.md` §6. Plane: RB1, RB2 (module *Corrections watcher & Rulebook*, owner Huy).

## Global Constraints
- A member never accepts its own rule: acceptance is a human action in the Members pane (or an org admin via API); the accepting actor is recorded.
- Append-only rules: `members.system_rules` grows by appending `\n\n- <rule>` with a marker comment `<!-- rule:<proposalId> -->`; the whole-member `PUT` remains for edits but the Rulebook never uses it (avoids the lost-update race).
- Rules reach the agent through the dispatch preamble (a fenced *Member rules* section) — never by mutating the workspace on the user's behalf except the explicit `.alicorn/rules/` commit, which happens only when the worktree is clean and the user has enabled it (`Settings → Members → Commit rules to the repo`, default on).
- `tenant_id` + RLS on `rule_proposals`; additive routes; i18n by tooling; no AI attribution.

## Decisions
1. Proposal text starts empty; the human writes it (an agent-drafted suggestion is a later enhancement).
2. Diff excerpt is captured by the corrections watcher (`git show --stat --patch <sha> -- <files>` truncated to 4 KB).
3. Rule file path `.alicorn/rules/<member-slug>.md`, one bullet per rule with the proposal id; commit message `rules(<member>): <first 60 chars of the rule>`.

## Tasks

### Task 1: Control API — `rule_proposals` + append endpoint
```sql
CREATE TABLE IF NOT EXISTS rule_proposals (id TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text, tenant_id TEXT NOT NULL, member_id TEXT NOT NULL REFERENCES members(id) ON DELETE CASCADE,
  outcome_id TEXT NOT NULL, verdict TEXT NOT NULL CHECK (verdict IN ('amended','rejected')), context JSONB NOT NULL, proposed_rule TEXT,
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','accepted','rejected')), decided_by TEXT, decided_at TIMESTAMPTZ, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), UNIQUE (tenant_id, outcome_id));
```
Routes: `POST /v1/rule-proposals` (from the drainer; idempotent on `outcome_id`), `GET /v1/members/:id/rule-proposals?status=pending`, `POST /v1/rule-proposals/:id/accept { rule }` → appends to `members.system_rules` (`UPDATE members SET system_rules = system_rules || $1, updated_at = now()`), marks accepted with `decided_by = auth.actor`; `POST /v1/rule-proposals/:id/reject`. Contract schemas `RuleProposalSchema`, `RuleProposalInputSchema`. Postgres route tests incl. idempotency, append, RLS.
