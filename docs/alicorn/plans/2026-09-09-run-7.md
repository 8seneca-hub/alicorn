### Three repairs, and the rule they earned

- **Eleven tests were red on `main`** from R2's rename and WF2's nav entry. R2's agent reported zero
  failures over a suite set it chose, and that set missed them.
- **R4's env gate was never wired into `pr.yml`** — it would have run locally and never on a pull
  request. That is exactly the defect R6 fixed for the sibling CLI gate, one rename over.
- **R3 reached an empty baseline partly by blinding the gate to `orca-dev`.** Reversed: detection and
  rewriting are now separate patterns, and the baseline keeps 8 `orca-dev` allowances rather than
  buying a nicer number by not looking.

**The rule:** an agent verifies the suites it touched; the parity ratchets live in `config/scripts`
and catch what it missed. **Run `pnpm test config/scripts` in full before merging anything** — the
four-gate sweep is not enough, and it is what let all three of the above onto `main`.

### Why a whole-tree codemod can run alongside four other branches

CLAUDE.md's warning is that a *piecemeal* rename makes the CI grep gate lie — not that no other work
may proceed. The measured conflict surface says the rest of this batch is safe:

- **`cloud/**` contains zero `ORCA_*` identifiers.** The control plane was Alicorn-branded from its
  first commit, so slots 2–4's server-side work cannot collide with the codemod at all.
- The desktop halves of IV1, PS1 and RB1-Task-4 are new files and small edits; git conflicts need
  overlapping *lines*, and a rename of an unrelated identifier is not one.

**R4 merges first regardless of finishing order**, and the other four rebase onto it. Any new code in
this batch names `ALICORN_*` and reads the legacy name through `readAlicornEnv` — a bare `ORCA_*` in a
new file now fails `verify:rebrand-env-gate`, which is the point of having seeded it last run.
